# ADR 0001 · 指针文件与内容寻址缓存

## 状态

已接受（2026-11-06 定稿；2026-11-27 随 pack_format 2 复核，结论不变）

## 背景

整合包仓库的主要内容是 jar、资源包与配置文件，其中 jar 体积大、来源多（Modrinth、直链、自有服务器），且同一文件会在多个整合包分支、多个实例之间重复出现。把二进制直接提交进 Git 会带来三个问题：

- 仓库体积随版本线性增长，克隆与 fetch 变慢；
- 无法表达「这个文件从哪来、能否重新获取」，仓库变成不可复现的二进制堆；
- 多个实例各自保存一份完全相同的文件，磁盘占用翻倍。

同时缓存本身不可信：磁盘损坏、用户手工替换、下载截断都会让缓存内容与期望内容不一致。若构建时直接信任缓存，会静默生成「哈希正确但内容错误」的整合包。

## 决策

- **指针文件**：仓库只保存以目标文件 SHA-256 命名的 `<sha256>.pointer`（JSON 文本），放在 `branch_config/` 下，内容形如 `{"sha256", "resolver", "metadata"}`。
- **路径与内容分离**：目标路径不写进指针，而由分支配置的 `file_manifest`（`相对路径 → sha256`）记录；同一个指针可被多个路径复用。
- **内容寻址缓存**：构建引擎默认把内容缓存在 `<workspace>/.cache/<sha256>`；bridge 对包内附带文件使用 `.hmcl/nsum/cache/files/`，可跨整合包复用。
- **零信任校验**：命中缓存必须重新计算 SHA-256，匹配才使用；不匹配则删除并重新下载。下载完成、写入落盘后同样要校验；任何一步失败都删除半成品，不留「看起来存在」的坏缓存。
- **解析器插件化**：下载地址由 `IPluginPointer` 解析器（`direct_url`、`modrinth`）给出，`BuildEngine::init` 扫描 EXE 同级的 `pointers/` 目录，确保导出插件内部的构建也能解析指针。
- **导出前物化**：构建阶段解析指针并写入真实文件，导出包内不保留 `.pointer`。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 二进制直接入库 | 实现最简单、离线可用 | 仓库膨胀、不可复现、多实例重复占盘 |
| 只存直链 URL | 仓库很小 | 链接失效即无法构建；无完整性依据；CDN 迁移需改全部记录 |
| 信任缓存不校验 | 构建最快 | 磁盘损坏/篡改会静默进入产物，排查成本极高 |
| 使用外部对象存储 | 仓库干净、容量大 | 引入外部依赖与费用；离线与镜像场景不可用 |

## 后果

- 正面：仓库只含文本与配置，克隆快；同一文件在分支与实例间共享缓存；哈希即校验依据，产物可复现；换下载源只需改指针 metadata，不动清单。
- 负面：首次构建必须联网解析并下载；指针与 `file_manifest` 必须成对维护，缺一会导致文件缺失或路径指向不存在的哈希；缓存目录需要清理策略。
- 影响范围：`NeoBuild`（指针下载、缓存）、`NeoCore`（`IPluginPointer` 契约）、编辑器指针面板、`.nsumpack` 导出与 bridge 安装流程。
